# Part 1 — The skill

**`untangle-codebase`** — original at `github.com/caldoai/skills` (426 stars, MIT, created 2026-10-25). Fetched from the upstream repo and verified byte-for-byte against the mirror in `sickn33/agentic-awesome-skills` (the mirror adds frontmatter metadata and safety sections; the workflow body is identical). One typo in the source, "a workaround om the codebase", corrected below.

```markdown
---
name: untangle-codebase
description: Untangle a whole codebase in one pass, so agents working in it read less
  per change, break less without noticing, and debug faster.
disable-model-invocation: true
argument-hint: "[optional area or concern to focus on]"
---

Start a thorough refactor of this codebase and complete it to the end.

Treat this as a goal.

**Why do this at all?**

- **Better output:** agents write better code in a well-structured codebase.
- **Cheaper & faster changes:** agents spend fewer tokens searching and more on the problem.
- **Fewer silent breaks:** agents break less without noticing.
- **Faster debugging:** agents find root causes faster.

**1. Ask**

Besides untangling the codebase, there are two other things you may do:

| Addition | What it does |
| --- | --- |
| **Comments** | Remove comments that only restate the code. |
| **Tests** | Remove tests that wouldn't catch a real bug, and fix the ones that fail without one. |

List these (with their exact descriptions) for the user and ask which ones to do. Then do only those.

**2. List every problem**

Don't change anything yet.

Go through the codebase asking one thing: **should these pieces change together?** Write down
every place the code gets the answer wrong, as in the decision log example. There are only
three ways to get it wrong.

**Hidden links:** pieces that must change together, where the code doesn't show it.

- Copies of logic or values: change one and the others must change too, but nothing says so.
- A module that reads a global or file set by another module: change that module and this
  one breaks, but nothing shows it (self-contained code).
- A feature split across folders by layer, or related code in different folders: one change
  needs all of them, but the layout hides that (domain-driven code, colocation).
- A call order or convention callers just have to know: change it and callers break, but
  nothing warns them (explicit over implicit).

**Needless links:** pieces tied together that change for different reasons.

- Callers that depend on internals: the internals change for their own reasons, and the
  callers break anyway (encapsulation).
- Stable code that imports something more volatile: the stable code has to change whenever
  the volatile code does (dependency direction).
- A general function with a parameter only one workflow understands: the function has to
  change whenever that workflow does (caller vocabulary).
- A shallow module: its interface changes whenever its internals do, so its callers change
  with it (deep modules).

**Surplus:** pieces with no reason of their own to change.

- Wrappers: they only change when the thing they wrap does (pass-through wrappers).
- Extension points and config for things that never vary: nothing will ever change them
  (speculative generality).
- Dead code: nothing uses it, so nothing will ever need it to change.

Also write down every **special case**: code that exists for one situation instead of
following from how the system works. Each one is a requirement the design never accounted
for, so use them to work out what the system needs to be.

- An `if` for one value
- A parameter for a specific caller
- A swallowed exception
- A retry or sleep
- A disabled test

**3. Redesign from first principles**

Work out the fixes as if the system had known today's requirements from the start. Look for
the one fix behind several problems, which often looks nothing like them. Don't fix special
cases one by one.

Ask the same thing of every fix, even one that looks better in the code: pieces that change
together end up together, pieces that don't aren't tied, and everything depends on what
changes less.

Write each fix above the problems it solves, as in the decision log example.

**4. Fix everything on the list**

Remove the special cases the redesign makes unnecessary, and keep the ones the system still
needs. Don't go looking for bugs separately. A structural fix may fix some along the way,
which is fine.

If the user chose Comments:

- Comments that restate the implementation, like `// sort first so the binary search works`,
  only change when it does, so they have no reason of their own to change. Remove them, even
  if they're phrased as a why.
- Comments about something outside the code, like `// the proxy drops websockets, so we poll`,
  change when that does, and the code can't show it. Keep them.
- Comments that explain a workaround in the codebase, like `// wait 100ms because the cache
  isn't ready yet`, only change when the problem behind the workaround does. They go when the
  redesign removes that problem.

If the user chose Tests, do this last, because tests are your regression safety net. A test
should fail on a regression, and only then:

- Tests that repeat the implementation only change when it does, so they have no reason of
  their own to change. They check the same interpretation against itself, so remove them.
- Tests tied to internals break when the code changes but behavior doesn't, so they change
  for the wrong reason. Rewrite them to depend on behavior, which changes less.
- Tests that can't fail pass whatever the code does, so no change ever affects them. They
  aren't checking anything, so remove them.

**5. Check, and repeat until done**

Have subagents search for special cases, hidden links, needless links and surplus.
**Do not stop until there is nothing worth fixing left.**

You're done when:

- **As few special cases are left in the system as possible.** How many remain is the best
  measure of how close you are.
- A typical change lands in one place.
- Every import is reasonable, and nothing imports anything more volatile than itself.
- Subagents have no issues left that are worth fixing.
- Intended behavior is the same as when you started, apart from bugs the refactor fixed.
  Test this at the end.

**Tips**

- **Start from a skeleton:** script away the function bodies, so the whole codebase fits in context.
- **Summarize with subagents:** have them summarize parts of the codebase, so you can reason
  across all of it at once.
- **Check the dependency graph often:** script one that shows what imports what, and rerun it
  as you go.
- **Enter where leverage is highest:** start looking there first.
- **Keep a decision log:** compaction is less of a problem that way.
- **Use Git as evidence:** for how often pieces change, and what changes together.
```

### My comments on the skill itself

It's better than most "clean up my code" prompts, and it earns that honestly. The organising idea is one sentence — *should these pieces change together?* — and everything else is a consequence of it. That's why it can produce a finite list instead of a vague mandate to "improve quality".

Three things it gets right that comparable prompts don't:

1. **It makes you ask permission before deleting anything.** The Comments and Tests options are opt-in, listed with exact descriptions, and tests are explicitly done last because they're the regression net. Most "cleanup" prompts quietly license an agent to delete the tests that were inconveniently failing.
2. **It insists on a written decision log before any edit.** Step 2 says *don't change anything yet*. That single constraint is what turns a refactor into something reviewable.
3. **It counts special cases as the progress metric.** "How many remain is the best measure of how close you are" is a falsifiable success criterion, which is rare in this genre.

Where I'd push back:

- **"Do not stop until there is nothing worth fixing left" is not achievable on a real codebase, and it's an invitation to keep going past the point of usefulness.** The skill's own mirror acknowledges this in a Limitations section the original lacks ("a whole-codebase pass can exceed one session"). Treat step 5 as a stopping heuristic, not a completion bar.
- **The redesign step is the risky one.** "Work out the fixes as if the system had known today's requirements from the start" is exactly the mindset that produces a big-bang rewrite. The guardrail against it is thin — one sentence telling you to look for the single fix behind several problems. On a large codebase, bound this step by directory or module before you start.
- **Nothing in the skill defines "intended behavior" or how to capture it.** Step 5 says "Intended behavior is the same as when you started… Test this at the end", but if the repo has weak tests, there is no baseline. Capture one yourself before step 4, or the whole thing is unverifiable.
- **It assumes subagents exist.** Step 5 hands the review passes to subagents; the original has no fallback. The mirror fixes this ("otherwise perform the review passes yourself").
- **The comment rule will delete useful comments if applied mechanically.** "Remove them, even if they're phrased as a why" is defensible in principle, but a comment recording a non-obvious invariant often looks like restatement. Read the diff on this pass.

Verdict: worth using, on a branch, with a captured baseline, and with step 5 treated as "stop when the returns flatten" rather than "stop when nothing is left".

## Two caveats the video skips

1. **"99%" is a benchmark score, not real-world reliability.** AndroidWorld is a controlled test suite. That's the difference between "wins the test" and "won't fat-finger your banking app." Don't read 99% as "safe to leave unattended."
2. **"Free tool" ≠ "free to run."** It's Apache-2.0, yes — but it needs a real device/emulator *plus* an LLM driving it (Claude Code/Codex), and that part is paid. So the free claim is true for the code, not for the whole setup.

## Why this one actually matters to us

This isn't just an interesting video — it lands directly on our prime directive. `WATCHER.md` §0 says the goal is **"the best AI coding agent operable from a phone."** ARTEMIS is literally the primitive for that: it lets an agent see and operate a real Android screen, and it exposes itself over MCP, which is exactly the interface our stack already speaks.

That's the §4.2 step I skipped last time — connecting the video to an open problem. Here it is concretely:

- **Open problem:** we can drive code, but we can't drive a *phone* — no verified way for the agent to tap/scroll/read a screen. That's the missing half of "operable from a phone."
- **What ARTEMIS gives us:** an Apache-2.0, MCP-native Android control layer we could test as that missing half.
- **Cost check (our card rule):** the repo is free, but the LLM behind it isn't — so this is "study it, maybe wire it to a key we already have," not "adopt as-is."

- **Strengths** — Google-backed, free, native MCP, 99%+ AndroidWorld, handles Canvas/Compose/Flutter, full screenshots + Logcat traces.
- **Weaknesses** — developer setup (Python/uv/ADB/scrcpy/FFmpeg, USB debugging), needs a paid LLM key, young (created 2026-08-13), Android-only, installs an Accessibility Service.
- **Opportunities** — real-device QA without a farm, CI regression tests, bug reproduction, and it could exercise the Amina/Miss Noor learner flows on a real phone.
- **Threats** — token cost at ~15–40 s/step (Pro), ADB-level trust surface, screen data going to a third-party LLM, app ToS.

```bash
git clone https://github.com/google/artemis.git && cd artemis
./start.sh                                  # auto-installs ADB, scrcpy, FFmpeg, uv deps
uv run artemis mcp --install all            # wires MCP into Claude Code / Codex / Cursor / …
uv run artemis run "Open Settings, check the battery level" --profile flash
```
